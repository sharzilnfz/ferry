# Landscape & technical research

## Scope

Research for a new open-source tool: secure, fast, cross-platform (macOS/Linux/Windows) full-file sync of dev project directories across machines over the internet, not VCS-based. Design goals under consideration: content-addressed store (git-objects/restic style), E2E encrypted by default, peer-to-peer with relay fallback. This document maps existing tools, what they do well, where they fail this use case, and the specific techniques worth borrowing.

## Techniques worth borrowing

### Syncthing BEP: protocol shape, temp names, conflicts

BEP is worth reading closely because it solved the same problems we face. Devices exchange their local models (file metadata plus block hashes); each device pulls missing blocks from peers holding them, forming a global model from highest-version vectors ([BEP v1 spec](https://docs.syncthing.net/specs/bep-v1.html)). Key mechanics:

- Never write destination files in place. All changes go to a temporary copy moved into place atomically. Temp names are `.syncthing.<name>.tmp` (Windows: `~syncthing~<name>.tmp` because leading-dot names are awkward there), with a hash substituted if the name would exceed path limits. Failed transfers keep the temp file up to a day to avoid re-fetching blocks ([Syncthing syncing docs](https://docs.syncthing.net/v1.0.0/users/syncing.html)).
- Verify every received block's SHA-256 before writing; discard mismatches and try another source ([docs](https://docs.syncthing.net/users/syncing.html)).
- Conflicts: when both sides changed a file differently, the older-mtime side gets renamed to `*.sync-conflict-<date>-<time>-<deviceid>*` rather than lost; equal mtimes break ties on the first 63 bits of device ID ([docs](https://docs.syncthing.net/users/syncing.html)). Users have asked for device *names* in conflict filenames for readability ([issue #3524](https://github.com/syncthing/syncthing/issues/3524)), a small UX lesson.
- Syncthing v2 (Aug 2025) migrated LevelDB → SQLite, dropped rolling-hash shifted-data detection for faster scans, and enabled multiple connections between v2 devices ([release announcement](https://forum.syncthing.net/t/syncthing-2-0-august-2025/24758), [Linuxiac coverage](https://linuxiac.com/syncthing-2-0-launches-with-major-database-overhaul)). The SQLite migration validates a structured index over KV-log storage for large folders.

Mutagen's algorithm is the other must-read for this section: it tracks "the most recently agreed-upon content" so each cycle is effectively a three-way merge between two endpoint states and the last common state, running in short cycles triggered by fs events ([Mutagen synchronization docs](https://mutagen.io/documentation/synchronization/)). That base-state tracking is what makes bidirectional sync safe without a journal of every change.

### Transport: QUIC, hole punching, DERP-style relay fallback

The proven architecture is layered: direct connection first, relay fallback that still preserves E2E.

- Syncthing uses local broadcast/multicast discovery, global discovery servers acting as a phone book mapping device ID → addresses, STUN for NAT type/address discovery, UPnP/NAT-PMP port mapping, QUIC listeners on the same port as TCP ([DeepWiki on STUN/NAT traversal](https://deepwiki.com/syncthing/syncthing/3.5-stun-and-nat-traversal), [forum explainer](https://forum.syncthing.net/t/discoveries-relays/8784)).
- Relays are dumb pipes forwarding already-encrypted bytes; the relay operator sees traffic volume and your IP/device ID, nothing else ([Relaying docs](https://docs.syncthing.net/users/relaying.html)). Relays are on by default so novice setups work behind NAT, and clients periodically retry direct connections and upgrade away from relays ([same docs](https://docs.syncthing.net/users/relaying.html)).
- Tailscale formalized the fallback design as DERP: connections start relayed through DERP over HTTPS port 443 and upgrade to direct WireGuard paths via DISCO negotiation; DERP never holds decryption keys ([DERP docs](https://tailscale.com/docs/reference/derp-servers), [connection types](https://tailscale.com/docs/reference/connection-types), [derp package](https://pkg.go.dev/tailscale.com/derp)). Peers are addressed by curve25519 public keys instead of IP addresses, which sidesteps address instability entirely. In 2025 Tailscale added user-designated high-throughput peer relays in front of shared DERP nodes ([peer relays blog](https://tailscale.com/blog/peer-relays-international-networks)).
- For QUIC-native designs, the IETF drafts on QUIC address discovery and NAT traversal coordinate path-validation attempts to create NAT bindings ([draft-seemann-quic-nat-traversal](https://www.ietf.org/archive/id/draft-seemann-quic-nat-traversal-02.html)), and the author's overview describes replacing STUN with QUIC extensions plus CONNECT-UDP-listen relays ([Seemann, A p2p Vision for QUIC](https://seemann.io/posts/2024-10-26---p2p-quic)). The iroh library implements this stack today: simultaneous-outbound-connection hole punching over QUIC, relay fallback, claiming ~90% direct-connection success across real networks ([iroh NAT traversal docs](https://docs.iroh.computer/concepts/nat-traversal)). iroh (Rust, MIT/Apache dual) is a plausible dependency instead of building traversal from scratch.

Recommendation-shaped summary: borrow the "always connect through relay first, upgrade to direct" flow, address peers by key not IP, and make the relay cryptographically blind. That combination is now field-proven three times over (Syncthing, Tailscale, iroh).

### Chunking: fixed vs rolling vs content-defined

- Fixed-size chunks (classic rsync): insertion near the start shifts every subsequent boundary, so most chunks mismatch after any prepend ([rsync tech report](https://rsync.samba.org/tech_report/), [cdc-file-transfer explanation](https://github.com/google/cdc-file-transfer)). Also slow: rolling hash misses force per-byte hash-map lookups; Google measured ~50 MB/s for rsync diffing versus 1500 MB/s for their CDC implementation ([README](https://github.com/google/cdc-file-transfer)).
- Rolling-hash fixed blocks (rsync sender-side): better, but still boundary-shift sensitive.
- CDC (restic, borg, Kopia, cdc_rsync): boundaries derive from local content via a sliding window (restic uses a 64-byte Rabin fingerprint window, cutting when low 21 bits are zero), so insertions shift boundaries only locally and downstream chunks survive unchanged ([restic CDC blog](https://restic.net/blog/2015-09-12/restic-foundation1-cdc/), [Gopher Academy walkthrough](https://blog.gopheracademy.com/advent-2018/split-data-with-cdc)). FastCDC improves throughput further ([FastCDC paper](https://www.usenix.org/conference/atc16/technical-sessions/presentation/xia), used by [google/cdc-file-transfer](https://github.com/google/cdc-file-transfer)). Reusable Go implementations exist: [restic/chunker](https://github.com/restic/chunker) (BSD-2).
- Security caveat that matters given E2E-by-default: chunk lengths leak information. A 2025 paper broke keyed-CDC schemes in Borg, Bupstash, Duplicacy, Restic, and Tarsnap with practical fingerprinting/key-recovery attacks, and proposes a provably secure KCDC construction ([Breaking and Fixing Content-Defined Chunking, eprint 2025/558](https://eprint.iacr.org/2025/558)). Restic 0.18 mitigated a related attack (recovering the chunker polynomial from observed chunk sizes) by randomly assigning chunks to pack files ([restic design notes](https://restic.readthedocs.io/en/stable/design.html)). If our content-addressed store lives on untrusted relays/storage, we should either use a provably secure KCDC scheme or ensure chunk-size patterns aren't observable.

For a content-addressed store specifically, restic's format is the cleanest reference: repository entries addressed by SHA-256 of content, write-once atomic files, trees deduplicated via deterministic JSON encoding, random polynomial per repo stored in config ([design doc](https://restic.readthedocs.io/en/stable/design.html)).

### E2E encryption and pairing UX

Three mature models to choose from:

1. Syncthing: each device generates a self-signed TLS cert; its SHA-256 fingerprint becomes the human-readable Device ID; connections require mutual TLS and the peer's fingerprint must be on an allow-list ([Security Principles](https://docs.syncthing.net/users/security.html)). Pairing = exchange device IDs out-of-band. Simple, no passwords, but trust-on-first-use of the cert and no at-rest encryption story beyond the transport.
2. restic/Kopia: password-derived master key (scrypt KDF) wraps per-repo keys; every blob independently encrypted and authenticated, `IV || ciphertext || MAC` layout ([restic design](https://restic.readthedocs.io/en/stable/design.html)); Kopia offers AES-256-GCM or ChaCha20-Poly1305 ([selfhosting.sh comparison](https://selfhosting.sh/compare/restic-vs-kopia-vs-borgbackup/)).
3. age as the envelope layer: small explicit keys, X25519 recipients, ChaCha20-Poly1305 STREAM-chunked payloads, passphrase/scrypt mode, SSH-key reuse, plugin ecosystem including YubiKeys and (as of mid-2025) passkeys ([filippo.io/age](https://pkg.go.dev/filippo.io/age), [C2SP spec](https://age-encryption.org/v1), [passkey support post](https://words.filippo.io/passkey-encryption)). Rust implementations exist ([rage](https://github.com/FiloSottile/age)), relevant if the tool is Rust.

Tether CLI demonstrates a pragmatic hybrid for dev tools: generate a random 256-bit key, wrap it with age under a user passphrase, commit the wrapped key to the sync backend, encrypt each file with AES-256-GCM and a fresh 96-bit nonce ([security architecture](https://tether-cli.com/security)). That gives multi-machine access with one memorable passphrase and zero-knowledge hosting. For team features, age public-key recipients map cleanly onto "share .env with teammates" flows, again per Tether's team sync ([teams page](https://tether-cli.com/teams)).

NaCl/libsodium secretbox is a fine primitive for chunk-level AEAD but has largely been superseded in new designs by AEAD constructions with explicit nonce management as in age STREAM or Kopia's GCM/ChaCha20 choices; whichever is picked, the 2025 KCDC attacks above argue for separating encryption design from chunking design deliberately rather than inheriting restic's exact scheme.

### File watching at scale

The three native mechanisms behave nothing alike ([detailed comparison](https://github.com/ishtms/nodebook/blob/main/chapters/04-file-system/04-watching-atomic-writes.md)):

- macOS FSEvents: recursive by design, tree-level, coalesces events, latency parameter, built for whole-disk monitoring. One stream covers 500k files.
- Linux inotify: precise per-inode events but non-recursive; recursive watch means one descriptor per directory. Default `fs.inotify.max_user_watches` is often 8192, regularly exhausted by `node_modules`; the queue overflow drops the entire inotify instance, which is fatal for most apps ([watchexec inotify limits guide](https://watchexec.github.io/docs/inotify-limits/), [fsnotify source comments](https://github.com/fsnotify/fsnotify/blob/master/fsnotify.go)).
- Windows ReadDirectoryChangesW: recursive with paired rename events, but a fixed-size buffer (64 KB typical) discards events on overflow (`ERROR_NOTIFY_ENUM_DIR`), forcing a rescan ([nodebook chapter](https://github.com/ishtms/nodebook/blob/main/chapters/04-file-system/04-watching-atomic-writes.md), [fsnotify WithBufferSize](https://github.com/fsnotify/fsnotify/blob/master/fsnotify.go)).

Mutagen's pragmatic policy is the best documented answer: use native recursive watches on macOS/Windows (with a cheap poll to detect watch-root deletion/recreation), and on Linux combine restricted native watches on recently-updated subtrees with polling, falling back to pure polling to avoid exhausting descriptors; polling interval defaults to 10 s ([Mutagen watching docs](https://mutagen.io/documentation/synchronization/watching)). Their rationale names our exact scenario: "imagine a synchronization root containing a `node_modules` directory." Ignore handling should follow gitignore conventions; both Mutagen and Bowline lean on "ignore anything you wouldn't check into source control" as the default posture ([Mutagen issue #102 discussion](https://github.com/mutagen-io/mutagen/issues/102), [Bowline vs Syncthing](https://bowline.sh/vs/syncthing)).

### Cross-platform pitfalls

These are where sync tools actually bleed users, and each is documented in prior art:

- Case-insensitive filesystems. Windows and macOS fold `file.txt`/`FILE.txt` together; case-only renames historically caused data loss in Syncthing pre-1.9.0, and the fix (a case-resolving filesystem wrapper with caching, `ErrCaseConflict` errors, NFC normalization comparisons) took years and multiple rewrites ([casefs.go](https://github.com/syncthing/syncthing/blob/main/lib/fs/casefs.go), [issue #1787](https://github.com/syncthing/syncthing/issues/1787), [PR #6717](https://github.com/syncthing/syncthing/pull/6717)). Plan for case-conflict detection from day one; don't repeat the five-year pain.
- Windows long paths. MAX_PATH is 260 chars; lifting it requires both the `LongPathsEnabled` registry value and a `longPathAware` manifest element in the application ([Microsoft docs](https://learn.microsoft.com/en-us/windows/win32/fileio/maximum-file-path-limitation)). A sync tool must handle long paths regardless of host opt-in, e.g. via `\\?\` prefixes. Note Syncthing hashes temp filenames when prefix+extension would overflow ([v1 syncing docs](https://docs.syncthing.net/v1.0.0/users/syncing.html)).
- Symlinks on Windows require developer mode or admin privilege to create; Unison supports Windows but treats symlinks carefully ([Unison manual](https://raw.githubusercontent.com/bcpierce00/unison/documentation/unison-manual.pdf)), and Mutagen forbids symlinked sync roots and refuses roots spanning filesystem boundaries ([Mutagen docs](https://mutagen.io/documentation/synchronization/)).
- POSIX permission/ownership mapping doesn't survive round trips to Windows; Resilio's own support response confirms their Sync product "is not intended for transferring file permissions" and applies defaults instead ([SoftwareAdvice review thread](https://www.softwareadvice.com/file-sharing/resilio-sync-profile/reviews)). Decide early what subset (exec bits? read-only?) is authoritative.
- NTFS alternate data streams, UTF-8 NFC vs OS-specific normalization (BEP mandates NFC for all names regardless of platform, [BEP spec](https://docs.syncthing.net/specs/bep-v1.html)), reserved Windows device names, and network-FUSE targets (where neither watching nor atomic rename behave, per [Mutagen issue #188](https://github.com/mutagen-io/mutagen/issues/188) and fsnotify docs noting notifications don't work on NFS/SMB/FUSE).

## What fails for agentic dev specifically, per competitor

- Syncthing: excellent plumbing, zero code semantics. It will faithfully replicate a corrupted `node_modules` from a Linux machine onto a Windows machine, and its GUI-first workflow fights terminal/agent automation. Bowline's entire pitch is built on this gap ([vs Syncthing](https://bowline.sh/vs/syncthing)).
- Mutagen: right algorithm, wrong topology for us. It assumes you name the endpoints; there's no discovery, no relay, no "my laptop finds my desktop." Container agent injection and Windows SSH server flakiness remain rough ([SSH docs](https://mutagen.io/documentation/transports/ssh/)).
- Cloud drives: agents writing thousands of files trigger rate limits and partial-upload states designed for documents, not builds. No E2E.
- git-annex/tether-cli: close in spirit (content addressing, encryption) but scoped to either large assets within git or dotfiles, not live full-project trees.
- The 2025/26 wave (Bowline, ByteSync, ConfigSync, tether-cli) confirms demand is real and unserved by free OSS: Bowline is commercial with unpublished internals, ByteSync is on-demand-only, ConfigSync advertises "open source" without a visible license or repository ([Bowline compare page](https://bowline.sh/compare)), and Tether doesn't attempt project-tree sync at all.

## Licensing/model notes for free OSS

- MPL-2.0 (Syncthing) and Apache-2.0/MIT (Mutagen, Kopia, cdc-file-transfer) permit building a competing tool and even vendoring components; GPL-3 (Unison, git-annex) is viral if we link, fine if we only read ideas. BSD-2 (restic, restic/chunker) allows unrestricted reuse including the chunker library directly ([chunker repo](https://github.com/restic/chunker)).
- Resilio shows the trap of proprietary freemium: home users get a crippled closed binary, commercial use needs seats, and the business line got retired into an enterprise platform ([EULA](https://www.resilio.com/legal/eula-subscription), [transition notice](https://www.resilio.com/sync-business)). An OSS core with optional hosted relay/discovery infrastructure (the Tailscale model) is the sustainable analogue: relays cost money to run, encryption makes them dumb, and self-hosting stays possible.
- Any hosted component (global discovery, relays) should be protocol-compatible with community deployments from day one, mirroring how Syncthing publishes relay and discovery server software so the network survives the project ([relay docs](https://docs.syncthing.net/users/relaying.html)).
