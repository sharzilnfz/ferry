# Scan throughput benchmarks

Owner ticket: T-004. SPEC M1 names scan throughput as the top risk; these
numbers are the acceptance gate for the incremental scan engine
(`crates/ferry-scan`). Re-run with:

```sh
cargo run --release -p ferry-scan --bin bench-gate
```

## Gate (from `.scratch/v1/issues/004-scan-watchers.md`)

Synthetic 100k-file / ~500 MiB fixture, deterministic pseudo-random content,
generated by the bench binary itself:

1. initial full scan < 60 s
2. incremental rescan after exactly 100 changed files < 2 s

Both measured ON THE RECORDING MACHINE.

## Results — Apple M1 (2026-08-24)

Machine: macOS 26.6.1 (BuildVersion 25G76); Apple M1; 8 cores; 8 GiB RAM.
Build: `cargo run --release`, rustc 1.97.1. Fixture: 100 dirs × 1000 files,
511,357,517 bytes (~487 MiB) of splitmix64-generated content.

| Metric                                        | Run 1   | Run 2   | Gate    |
|-----------------------------------------------|---------|---------|---------|
| Initial full scan                             | 25.72 s | 27.49 s | < 60 s  |
| Incremental rescan after 100 changed files    | 0.374 s | 0.361 s | < 2 s   |

Correctness assertions inside the same runs:

- mutation set vs previous manifest is EXACTLY 100 `content_modified`
  (`ferry-store::diff_manifests`; zero spurious adds/removes/metadata),
- a follow-up zero-change pass hashes 0 bytes (size/mtime/exec
  short-circuit proof at scale),
- incremental pass rebuilt 163 dirs (100 files + ancestor closure),
  rehashed exactly those 100 files: ~501 KiB hashed in total.

**Verdict: both gates PASS with ≥2× headroom on the initial scan and >5×
on the incremental rescan.**

## Results — Apple M1 (2026-08-26, after chunker memoization)

Same machine and fixture. Changes since the 2026-08-24 table: the chunker
derives its slide-out power + fold table once per polynomial for the life
of the process instead of once per chunked file (ticket 06 / C3), and the
incremental walker reuses one read buffer + one chunk scratch buffer
across files instead of allocating 256 KiB per rehashed file.

| Metric                                        | Run 1   | Run 2   | Gate    |
|-----------------------------------------------|---------|---------|---------|
| Initial full scan                             | 21.40 s | 23.37 s | < 60 s  |
| Incremental rescan after 100 changed files    | 0.427 s | 0.368 s | < 2 s   |

Initial full-scan throughput improves ~15–20% (25.7–27.5 s → 21.4–23.4 s);
the per-file warm-up elimination dominates because every one of the 100k
files previously paid irreducibility + `x^504` + a 256-entry table build.
Incremental rescan stays well inside the gate (noise-band overlap with the
old numbers; the 163 rebuilt dirs are dominated by IO, not setup).
Correctness assertions identical to the previous run (exact mutation set,
zero-change pass hashes 0 bytes).

## Methodology

- **Fixture**: generated fresh by the bench binary into
  `target/scan-fixture-100k` (git-ignored). Sizes vary deterministically per
  file index (2048–8191 B), content is a splitmix64 byte stream — no
  external corpus, fully reproducible across machines and runs.
- **Store location**: `.ferry` lives INSIDE the watched root (the realistic
  layout), which exercises the engine's structural exclusion of the store
  directory from scans and watches. The store uses `PassthroughCipher`
  deliberately: the gate isolates scan/chunk/store cost from encryption,
  which would otherwise be a near-constant per-byte multiplier (ChaCha20-
  Poly1305) unrelated to watcher or walk performance.
- **Initial gate timing** covers `ScanEngine::watch_with`, whose synchronous
  first act is a whole-tree pass (every file read, CDC-chunked through the
  folder polynomial, hashed BLAKE3, staged into packs).
- **Incremental gate timing** measures the completed PASS duration recorded
  in `PassStats::duration` (walk + hash + store IO for the dirty subtrees),
  NOT debounce/event latency: after rewriting the 100 files we allow events
  to settle (<1 s of wall clock), then either the worker's debounced pass or
  an explicit `scan_once()` performs the work; whichever executes it records
  the duration. Notification latency is an engine-quality property tested
  separately (integration tests assert settled updates within seconds).
- **Chunking**: restic-lineage Rabin fingerprint, 512 KiB min / 8 MiB max
  (`docs/store-format.md`). Files are far below MIN_SIZE, so each file is
  one chunk; per-file overhead (open/stat/read/hash/pack-stage) dominates
  the initial scan, which is why parallel hashing was not needed to clear
  the gate.

## Interpretation & next levers

- Initial throughput ≈ 17–19 MiB/s end-to-end single-threaded. The chunker's
  byte-at-a-time GF(2) loop is the known hot spot (ferry-store T-002 ships
  tables but stays scalar). If a future fixture (e.g. many large files)
  misses a gate, the ordered levers are: (1) hash-while-chunking overlap,
  (2) parallel per-file hashing across std threads (content addressing makes
  this trivially safe), (3) chunker table warm-up per folder.
- Incremental cost scales with DIRTY SUBTREES (163 rebuilt here because the
  100 targets spread across the tree), not tree size: untouched siblings are
  not even stat'd. A burst confined to one directory should be faster still.
- Re-run before touching the walker, the chunker parameters, or anything in
  the pack write path; regressions here are user-perceived latency (SPEC
  risk list).
